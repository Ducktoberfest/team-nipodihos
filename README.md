# FoundIt — AI-powered lost & found matching

> **Lost something on campus?** FoundIt compares your description with items other people
> have found — even when they describe it in completely different words — and explains
> **why** each suggestion might or might not be your item.

Built in one day at a hackathon by **Team Nipodihos**, using an **open-weight language model**
(`gpt-oss-120b`, Apache 2.0).

---

## The problem

Lost-and-found systems match items by keywords or not at all. But people describe the same
thing differently:

| Lost report | Found report |
|---|---|
| "I lost my **dark blue backpack** near the **university library**. It had a laptop and a small **keychain** inside." | "A **navy school bag** was left on a chair in the **library**. It has a **keyring** attached." |

A keyword search sees almost no overlap. A human sees an obvious candidate.
At the same time, a dark blue backpack found in the *Sports Centre* the *day before* is
**not** a good match, even though it shares the color and category.

FoundIt is designed to tell these apart, and to say *why*.

---

## What FoundIt does

1. **Submit** a lost or found report: description, category, color, location, time, and an
   optional **private detail** (e.g. "the keychain is a small silver Eiffel Tower").
2. **Find matches:** the AI agent searches reports of the opposite type and returns a
   ranked list of candidates.
3. **Understand each suggestion:** matching evidence (green), conflicting evidence (red),
   missing information, a transparent ranking score, and a recommended next step.
4. **Confirm, reject, or mark uncertain** — and verify ownership before any handover.

---

## How the AI agent works

A small, controlled pipeline — not a free-roaming autonomous agent. The model does what
language models are good at; trusted Python code does everything that must be reliable.

```
 New report ──▶ extract    [model]   "navy school bag" → item: backpack, color family: blue
                                      saved with the report

 Find matches ─▶ 1. retrieve [Python]  opposite type, compatible category, word similarity → top 5
                 2. compare  [model]   ONE call compares all candidates; strict JSON output
                 3. verify   [Python]  every quoted piece of evidence must appear word-for-word
                                       in the reports, otherwise it is discarded
                 4. score    [Python]  fixed points table + safety rules → ranked results
                 └─ model unavailable? → "degraded mode": rule-based results, never "likely"
```

**Design principles**

- **The model suggests; Python decides.** The model never sets the score, never touches the
  database, and never runs code or SQL.
- **No invented evidence.** Each claim must quote the reports verbatim; unverifiable claims
  are dropped before anyone sees them.
- **Missing information is never treated as a match.** It scores 0 and is listed as "still unknown".
- **Time is checked by code, not the model.** An item found *before* it was lost is flagged automatically.
- **Privacy by design.** Contact info is never sent to the model or returned by the API.
  The finder's private detail is shown only as `🔒 private detail withheld` — the real owner
  must describe it to prove ownership.
- **It never crashes the demo.** If the model fails, the API still answers with rule-based
  results and a clear "AI unavailable" flag.

### The ranking score (not a probability)

The score is a transparent sum of points, used only to order candidates. It is **not**
a calibrated probability and is never generated by the model.

| Attribute | Max points | Full points when… |
|---|---|---|
| Category | 30 | same kind of item ("school bag" ≈ "backpack") |
| Color | 20 | compatible color ("navy" ≈ "dark blue") |
| Location | 20 | same place |
| Time | 15 | found within 3 days after it was lost |
| Features | 15 | distinguishing details agree (incl. private details) |

"Partial" agreement earns half; "unknown" and "conflict" earn 0. Safety rules then cap the
assessment — e.g. a category or time conflict, or a contradicting private detail, always
means **unlikely match**, whatever the model suggested. Full rules: [`docs/API.md`](docs/API.md).

## The model and why it qualifies

| | |
|---|---|
| **Model** | [`openai/gpt-oss-120b`](https://huggingface.co/openai/gpt-oss-120b) (fallback: `gpt-oss-20b`) |
| **License** | **Apache 2.0** — open-weight; weights are publicly downloadable |
| **Hosting** | [Groq](https://console.groq.com) (OpenAI-compatible API, free tier). We have no GPU, so we use hosted inference; the same open weights could run on any server without code changes. |
| **Role** | Normalizes report descriptions and compares reports with evidence. It is the component that understands synonyms, shades and free-text details. |

We tested the riskiest assumption first ([`scripts/spike_model.py`](scripts/spike_model.py)):
on 4 hand-made tricky cases, the model produced schema-valid JSON, all four assessments
were sensible, every quoted piece of evidence was found in the source reports, and no private
details leaked — in about 5 seconds per call. *(A small sanity check, not a benchmark.)*

**Photos:** we are evaluating an open-weight vision model (`qwen/qwen3.8-27b` on Groq).
It will only be used for matching if it passes our tests on real photos; otherwise photos are
shown to humans but not analyzed.

## Architecture

```
React + Vite (frontend/)  ──HTTP/JSON──▶  FastAPI + SQLite (backend/app/)
                                                   │ Python call
                                                   ▼
                                     AI agent (backend/foundit_ai/) ──▶ Groq: gpt-oss-120b
```

| Layer | Tech | Folder |
|---|---|---|
| Frontend | React, Vite, plain CSS | `frontend/` |
| API | Python, FastAPI, Pydantic | `backend/app/` |
| Storage | SQLite (single file) | `backend/foundit.db` (not committed) |
| AI agent | Python, `openai` SDK → Groq | `backend/foundit_ai/` |
| Tests | pytest (fully offline, fake model) | `backend/tests/` |

**API** (full contract with request/response schemas: [`docs/API.md`](docs/API.md))

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/reports` | Create a lost or found report |
| `GET` | `/reports` | List reports |
| `GET` | `/reports/{id}` | Report details (public view) |
| `POST` | `/reports/{id}/matches` | Run the AI agent, return ranked candidates |
| `GET` | `/reports/{id}/matches` | Last saved results |
| `POST` | `/matches/{id}/feedback` | Confirm / reject / uncertain |

## Getting started

**Requirements:** Python 3.11+, Node 18+, Git, a free Groq API key.

```bash
git clone https://github.com/Ducktoberfest/team-nipodihos.git
cd team-nipodihos
```

**1. Secrets** — copy the template and add your key (get one at https://console.groq.com/keys):
```bash
cp .env.example .env        # Windows: copy .env.example .env
```
`.env` is git-ignored. Never commit it or paste your key anywhere else.

**2. Backend + AI**
```bash
python -m venv .venv
.venv\Scripts\activate                       # macOS/Linux: source .venv/bin/activate
pip install -r backend/requirements.txt      # until the backend is merged: backend/requirements-ai.txt
python -m pytest                             # offline tests, no API key needed
python scripts/seed_db.py                    # load demo reports (once available)
uvicorn app.main:app --reload --app-dir backend
```
API docs: http://localhost:8000/docs

**3. Frontend**
```bash
cd frontend
npm install
npm run dev
```
Open http://localhost:5173

## Demo walkthrough

1. Open the app and browse the seeded campus reports.
2. Submit the lost report: *"I lost my dark blue backpack near the university library. It had
   a laptop and a small keychain inside."* with private detail *"Keychain is a small silver Eiffel Tower."*
3. Click **Find matches**. Expected:
   - **Likely match** — the *navy school bag* in the library: synonyms recognized, the
     finder's private detail is consistent but stays hidden 🔒.
   - **Unlikely** — a *blue backpack in the Sports Centre*: different building, found the day
     **before** the loss, and "no keyring".
   - **Unlikely** — a *dark blue backpack* in the library café that looks identical, but the
     finder's private detail contradicts yours.
   - **Not enough info** — "a backpack handed in at the security desk".
4. Confirm the likely match after "verifying" the keychain.
5. Remove the API key and restart: matching still works in **degraded mode** with a clear banner.

## Limitations

- The ranking score orders candidates; it is **not** a probability that two reports are the same item.
- A suggestion is never proof of ownership. Users must verify before any handover.
- Evaluated on a small hand-made campus dataset, in English only.
- Depends on a hosted inference provider; free-tier limits (~8K tokens/min) allow roughly
  2–4 matching runs per minute. When the model is unavailable, results fall back to simple rules.
- No user accounts or authentication (out of scope for a one-day MVP); a real deployment
  would need them to protect report data.
